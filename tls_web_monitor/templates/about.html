🎯 Project Objective & Scope Capstone Specification

Modern web applications operate in an adversarial threat landscape characterized by automated botnets, credential stuffing, injection probes, and out-of-band database tampering. This university capstone project develops an integrated, full-stack cybersecurity defense system that unites transport-layer encryption (TLS/HTTPS), secure user authentication and RBAC, real-time HTTP telemetry and persistent SQLite logging, cryptographic tamper-evident HMAC audit verification, and a rule-based server-side threat detection engine.

Core Language:
Python 3.13 / 3.12
Web Framework:
Flask 3.1
Transport Security:
Python ssl (TLS 1.3 / 1.2)
Database & Audit:
SQLite3 + Cryptography HMAC
🔐 Module 1: TLS-Based Secure Communication and Authentication Module 1

Provides an encrypted, authenticated transport tunnel and user access framework:

  • TLS Context Hardening: Configured with Python's ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER). Enforces TLS 1.2 / TLS 1.3, blocks weak ciphers and insecure legacy versions (SSLv2, SSLv3, TLS 1.0, TLS 1.1).
  • X.509 Development Certificates: Auto-generated with 2048-bit RSA keys and Subject Alternative Names (SAN) for localhost and 127.0.0.1 via the cryptography library.
  • PBKDF2 Password Hashing: Passwords hashed with salted PBKDF2-HMAC-SHA256 via Werkzeug. Zero plaintext passwords stored.
  • Session & Cookie Security: Cookies hardened with HttpOnly=True, SameSite=Lax, and dynamic Secure=True over TLS. Permanent lifetime capped at 2 hours.
  • CSRF Defense: Cryptographic CSRF tokens validated on all state-changing POST requests using constant-time verification (hmac.compare_digest).
  • Security Headers: Enforces HSTS, CSP, X-Content-Type-Options, X-Frame-Options, and Referrer-Policy.
📡 Module 2: Web Application Monitoring and Logging Module 2

Provides continuous request telemetry, persistent database audit logs, and cryptographic verification:

  • Telemetry Hooks: Intercepts all requests via Flask before_request and after_request hooks, capturing timestamp, client IP, method, requested path, response code, and latency (ms).
  • Sensitive Data Redaction: Sanitizes query parameters and request bodies, strictly excluding passwords, tokens, cookies, and authorization headers from audit storage.
  • Search, Filter & Export: Multi-parameter log console with pagination, search keywords, category filters, and CSV export.
  • Cryptographic Tamper-Evidence: Every log row is signed with an HMAC-SHA256 tag over canonical row data.
  • Integrity Audit Engine: Scans SQLite records and flags any record inserted, edited, or deleted directly in the database without authorization.
  • Security Limitations: Local HMAC protects against unauthorized file modification. In production enterprise deployments, local logs must be supplemented with real-time TLS forwarding to an append-only WORM SIEM.
🚨 Module 3: Threat Detection and Security Analysis Module 3

Autonomous server-side rule engine inspecting ingress requests for malicious activity:

  • SQL Injection (SQLi) Detection: High-severity detection of UNION SELECT, boolean tautologies (' OR '1'='1'), destructive DDL commands, and comment truncations.
  • Path Traversal (LFI) Detection: Flags path backtracking sequences (../, ..\) and sensitive operating system files (/etc/passwd, win.ini).
  • Brute Force Detection: Monitors consecutive failed login attempts within a configurable time window (default: 5 failures / 5 minutes) and alerts on credential stuffing.
  • Rate Limiting / Request Bursts: Detects rapid request floods exceeding threshold (default: 60 req/min) from a single IP.
  • Unauthorized Access Probing: Flags repeated 401/403 access denials targeting protected administrative routes.
  • Defense-in-Depth Principle: Detection rules provide real-time alerting but do not replace preventive controls. All SQL queries strictly use parameterized statements (?).
🔒 Understanding Development TLS Certificates & Browser Warnings Security Concept

When visiting https://localhost:8443, your web browser (Chrome, Edge, Firefox) displays a warning screen (such as "Your connection is not private" or NET::ERR_CERT_AUTHORITY_INVALID).

Why Does the Warning Appear?

The TLS tunnel is fully encrypted using 2048-bit RSA and modern AES-GCM ciphers. However, the certificate was generated locally and signed by its own key (self-signed) rather than a commercial Root Certificate Authority (like Let's Encrypt or DigiCert) trusted by the operating system trust store.

How to Safely Trust it in Development:

1. In Chrome/Edge: Click Advanced → Proceed to localhost (unsafe).
2. On Windows: To eliminate warnings permanently, import certs/cert.pem into Trusted Root Certification Authorities via certmgr.msc.
3. In production, obtain an officially signed certificate and place the app behind a reverse proxy (e.g. Nginx).
